## 2. 接缝 ① · 任务字段与落地短链 ★最关键、也最好解决★

### 我方的理解（请确认是否正确）

- `batchImport` 中 `data[]` 的字段定义**由任务的话术配置决定**
- 我方任务 **「接口测试01_74691」当前的字段定义只有 `phoneNum`**
- 挂机短信内容配置在 `sms_config.sms_info[].sms_content`，**按 `tag_code` 分类，是任务级固定文案**

### Q1 · 请在我方任务的话术配置中增加两个字段

| 字段 | 类型 | 用途 |
|---|---|---|
| `traceId` | String（32 位以内） | 我方归因标识。**只需在结果回调的 `input_params` 中原样带回即可**，通话中不使用 |
| `shortUrl` | String | 我方逐条生成的落地短链 |

### Q2 · `sms_content` 是否支持占位符引用上传字段？

例如配置为：

```
【签名】详情请点击 ${shortUrl}
```

其中 `shortUrl` 取自我方 `batchImport` 时逐条上传的值。

> **若支持**：一人一链，归因精确到单次外呼，这是最优解。
> **若不支持**：我方将改为「收到结果回调后由我方自行发送短信」，
> 不占用贵方短信通道 —— 但请明确告知，以便我方定方案。

## 3. 接缝 ② · 页面行为的实时上行

### 我方的理解（请确认）

贵方文档中的接口分两类：**客户主动调用**（任务信息、批量导入、批次查询、黑名单）
与**贵方回调客户**（数据执行结果、短信状态、短信回执、AI转人工、人工回拨、人工短信、人工点呼）。
**未见「客户向贵方实时推送页面行为」的通道。**

### Q3 · 该能力是需要新增，还是已有未公开的接口？

我方希望在客户点击落地页后，**实时**将页面阶段事件推送给贵方，供通话中的 AI 引导使用。

**我方口径已定，作为输入规格提供**（非待协商格式）：

**事件（11 个）**

`LINK_CLICKED` / `PAGE_LOADED` / `PAGE_LOAD_FAILED` / `STAGE_ENTERED` / `STAGE_LEFT` /
`STAGE_STUCK` / `STAGE_BACKWARD` / `SUBMIT_ATTEMPTED` / `SUBMIT_BLOCKED` /
`PAYMENT_ENTERED` / `SESSION_ENDED`

**阶段枚举（产品无关）**

`LANDING` → `PLAN_SELECT` → `INFO_FILL` → `DISCLOSURE` → `CONFIRM` → `PAYMENT` → `DONE`

**结构**

```json
{
  "traceId": "0812B7014",
  "taskItemUuid": "bed123eede3f447c9ba0889d1a304d1f",
  "eventCode": "STAGE_STUCK",
  "stage": "DISCLOSURE",
  "productLine": "HEALTH",
  "elapsedMs": 45000,
  "timestamp": 1755000000000
}
```

**若需新增，请给出可行性判断与排期。** 我方其余开发不依赖此项，可先以 Mock 推进。

### 关于 `DISCLOSURE` 的粒度

该阶段作为一个整体上报，**原因是我方当前投保页的告知环节就是一个确认勾选，
没有逐项问询** —— 可上报的粒度仅止于「是否勾选、停留多久」，没有更细的可给。

若后续产品改为逐项告知，届时再与贵方讨论粒度。

## 4. 接缝 ③ · 口头退订必须独立回传

### Q4 · 客户在通话中明确表示「不要再打了」，能否作为独立字段回传？

我方已确认：结果回调中仅有 `tag_code` / `tag_desc`（自动化结果）
与 `modify_tag_code` / `modify_tag_desc`（人工标注），
人工侧有 `follow_stage` / `agent_note` 但为自由文本 —— **均非结构化的退订信号**。

建议增加 `opt_out: Boolean`（或等效的固定 `tag_code`）。

> **这是合规硬需求，不是体验优化。** 意向等级与退订在我方是两套处理逻辑：
> 意向低可换产品再触达，**退订不可**。
> 目前我方 DNC 的唯一来源是短信回执「退订回T」，**电话中的口头退订完全收不到**。

## 5. 接缝 ④ · 回调端点安全

### Q5 · 回调能否增加 HMAC 签名 + 时间戳？

贵方文档《认证 · 2.方法回调的认证》建议：

> 客户可以通过校验请求源 ip 的方式（通过 `x-real-ip`、`x-forwarded-for` 这 2 个 http header 获取）来达到认证的目的。

**这两个 header 由请求方自行填写，可被伪造。** 我方可在网关层取真实
`remote_addr` 并按贵方出网 IP（`47.99.72.114` 及人工类的四个）做白名单，
但**希望增加与主动调用同款的 `x-access-sign` 签名机制**作为第二道校验。

> 回调端点写入的是转化数据，将用于双方结算与效果评估，**被灌入伪造数据则全部作废**。

### Q6 · 回调重试时 payload 是否完全一致？

已知：数据执行结果推送失败重试 **2 次、间隔 10 分钟**；
短信与人工类回调失败重试 **6 次、间隔 10 分钟**。

请确认**重试时的报文与首次是否逐字节一致**（含时间戳字段）——
我方需据此做幂等去重。若不一致，请指明可用作幂等键的字段
（我方倾向 `task_item_uuid` + `call_uuid`）。
